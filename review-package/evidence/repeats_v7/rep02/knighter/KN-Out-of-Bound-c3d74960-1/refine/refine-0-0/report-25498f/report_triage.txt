- Reason: The reported loop does not match the target bug pattern. `hpd_rx_irq_work_suspend()` indexes `dm->hpd_rx_offload_wq[i]`, not `secure_display_ctxs[i]`. This HPD offload-workqueue array is sized and initialized using `dm->dc->caps.max_links`, because it represents per-display-link HPD receiver work, whose natural bound is the number of DC links rather than the number of DRM CRTCs. `num_crtc` describes available display pipelines/CRTCs and may legitimately differ from `max_links`; it is not the capacity invariant for this array.

  The loop starts at `i = 0` and executes while `i < dm->dc->caps.max_links`, so its largest accessed element is `hpd_rx_offload_wq[max_links - 1]`. With allocation/initialization using the same `max_links` count, valid indices are exactly `[0, max_links - 1]`; there is no off-by-one or allocation/iteration mismatch. A larger `max_links` than `num_crtc` therefore does not make this access out of bounds. It instead means the driver flushes HPD workqueues for links that may not currently have an associated CRTC, which is expected.

  The null check also handles allocation failure at the array-pointer level: if `hpd_rx_offload_wq` was not allocated, the function performs no indexed access. In normal driver lifetime, suspend runs before display-manager teardown, while the corresponding fini path flushes/destroys the same `max_links`-bounded workqueues and frees the array. The target fix would change an array whose capacity should be `num_crtc`; applying that change here would be semantically incorrect and could omit valid per-link workqueues.
