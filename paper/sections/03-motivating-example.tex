We illustrate the refinement process end to end on a single case: the KNighter-derived CSA checker for Linux commit \texttt{97cba232549b}, which repairs an off-by-one access in the AMD display driver~\cite{linuxCommit97cba232,yang2025knighter}.
This case is small enough to inspect manually yet exhibits the core problem: the generated checker recognizes a look-ahead access but misses the relation between the loop bound and the array's capacity.

\subhead{The bug and its patch.}
The array \lstinline|dc->links| has a declared capacity of \lstinline|MAX_PIPES * 2|, abbreviated as $N$ in Figure~\ref{fig:motivating} (\cmark{1}).
The function \lstinline|get_host_router_total_dp_tunnel_bw| iterates over these links.
On a matching host-router branch, the loop body reads both \lstinline|links[i]| and \lstinline|links[i + 1]| (M10--M11, \cmark{3}).
Under the original bound $i<N$ (M5, \cmark{2}), the loop allows $i=N-1$, so the look-ahead reaches index $N$ and overflows the array.
The patch tightens the bound to $i<N-1$ (M6, \cmark{4}), capping the largest look-ahead index at $N-1$.

\subhead{Why the baseline checker fails.}
The generated checker already recognizes an induction variable, a loop bound, and a look-ahead subscript.
It warns whenever the access lacks a protective condition in an enclosing \lstinline|if| (B1--B5, \cmark{5}).
This rule checks only the branch guards and overlooks the protection carried by the loop bound itself.
Because the fixed program still contains \lstinline|links[i + 1]|, the checker fires on both revisions despite the tighter bound, yielding \texttt{1/1} alerts in independent replay.
KNighter's own refinement loop does not change this checker: its report-driven policy finds no actionable feedback on this case, so the output remains \texttt{1/1}.
In short, the checker has learned that a look-ahead access needs a guard, but not that the loop condition already provides one.

\subhead{Our refinement with analyzer evidence.}
\toolname starts from the same validation symptom (\texttt{1/1}) but goes further by assembling analyzer-internal context alongside the patch and source.
Specifically, it collects four evidence records: two from Clang~18 internals (a CFG dump via \texttt{debug.DumpCFG} and a call graph via \texttt{debug.DumpCallGraph}) and two from analyzer output.
The CFG exposes the loop structure and branch context that the checker misses. The patch and source records identify the bound change.

With this evidence, the LLM adds a capacity-aware condition to the existing \lstinline|checkASTCodeBody| traversal.
The refined checker reads the declared array extent from the AST type and computes the maximum look-ahead index: for a loop $i<B$, that index is $(B-1)+1=B$.
It suppresses the warning when $B$ is smaller than the array extent $N$ (C3--C6, \cmark{6}).
Under the vulnerable bound $B=N$, the maximum index equals the extent, so the warning fires.
Under the fixed bound $B=N-1$, the maximum index is safely below the extent, so the checker stays silent.
Crucially, this condition is based on type and index relations rather than the patched function name, a specific capacity constant, or adjacency of statements.
The first candidate passes independent Linux replay at \texttt{1/0}.

\subhead{Benefits over the baseline.}
The refined checker offers two concrete advantages over KNighter's refined output.
First, higher precision on the original Linux pair: \toolname's checker correctly reports \texttt{1/0} (warns on the vulnerable revision, stays silent on the fixed one), whereas KNighter's checker remains at \texttt{1/1} because it never learned the bound-to-capacity relation.
Second, better generalization: on 114 controlled C programs built from the same look-ahead pattern (with varied names, capacities, unrelated statements, and loop-bound formulations), \toolname's checker gives the expected result on all 114 executions (58 unsafe warned, 56 safe silent), while the checker produced by KNighter's refinement loop correctly handles only 31 unsafe and 25 safe cases. AddressSanitizer independently confirms the safety labels for 80 of these variations~\cite{serebryany2012asan}.
Both advantages stem from the same root cause: analyzer evidence (CFG and call-graph context) lets the model understand why the loop bound matters for safety, so the refined checker encodes a semantic condition (maximum index vs.\ array extent) rather than matching syntactic patterns.
