\toolname is a post-synthesis refinement layer for LLM-generated vulnerability detectors.
Given a draft CSA checker or CodeQL query produced by an upstream generator, the patch that motivated the synthesis, and the corresponding source tree and validation scope, \toolname refines the detector to recover vulnerable-side warnings or reduce fixed-side reports.

Figure~\ref{fig:approach-architecture} summarizes the workflow across five stages.
\textbf{(a)~Generator context.} \toolname receives a draft detector, patch, source tree and validation target. It treats the generator as a black box and refines its output in place.
\textbf{(b)~Evidence assembly.} Rule-guided preflight selects evidence requirements, and four collectors gather patch facts, source context, analyzer evidence and validation feedback.
\textbf{(c)~Evidence bundle.} The facts are normalized into typed records with their origin and source bindings.
\textbf{(d)~Refinement.} The agent edits the latest attempt using a bounded view of those records. Paired validation updates a separate best retained detector.
\textbf{(e)~Audit artifacts.} Each run persists evidence, prompts, replies, candidates and validation results, so a refinement can be inspected or resumed.
The audit links the retained checker to the evidence shown, attempted edits and paired outcomes; RQ3 compares refinement with and without native evidence.

\begin{algorithm}[t]
\footnotesize
\caption{Paired-Warning Evidence-Guided Refinement}
\label{alg:evidence-guided-refinement}
\begin{algorithmic}[1]
\Require detector $D$, patch $P$, source $S$, scope $V$, backends $A$, budget $K$
\Ensure refined detector $D^*$ and audit report
\State $R_0 \gets \Call{Validate}{D,P,V}$
\State $E_p,E_s \gets \Call{Preflight}{P},\ \Call{ExtractSource}{P,S,D}$
\State $E_a \gets \bigcup_{a\in A}\Call{CollectNative}{a,D,P,S}$ \quad $E_v \gets \Call{Feedback}{R_0}$
\State $B \gets \Call{NormalizeMerge}{E_p,E_s,E_a,E_v}$
\State \textbf{if} $\Call{PDS}{D,P,V}$ \textbf{then return} $\Call{Audit}{D,B}$
\State $D^* \gets D$ \quad $L \gets D$ \quad $T \gets \Call{InitialStopState}{}$
\For{$i=1$ to $K$}
  \State $V_i \gets \Call{BoundedView}{B}$ \quad $C_i \gets \Call{AgentEdit}{L,P,V_i}$
  \State $R_i \gets \Call{ValidateIfCompilable}{C_i,P,V}$
  \State \textbf{if} $\Call{Accept}{C_i,D^*}$ \textbf{then} $D^* \gets C_i$ \Comment{Equation~\ref{eq:accept}}
  \State $L \gets C_i$ \quad $E_i \gets \Call{Feedback}{R_i}$
  \State $B \gets \Call{Merge}{B,E_i}$
  \State $T \gets \Call{UpdateStopState}{T,R_i,D^*}$
  \State \textbf{if} $\Call{Stop}{T,K}$ \textbf{then break}
\EndFor
\State \Return $\Call{Audit}{D^*,B}$
\end{algorithmic}
\end{algorithm}

\subsection{Evidence Selection and Exposure}
\label{sec:adaptive-selection}

The central design choice in evidence assembly~(Figure~\ref{fig:approach-architecture}b) is \emph{what to collect}.
Analyzer outputs can be large and heterogeneous.
Passing them wholesale to the model dilutes the facts relevant to the checker under refinement.
\toolname limits collection to patch-related source and presents selected evidence roles through bounded views.

\subhead{Rule-guided preflight.}
PatchFacts Extractor parses affected functions, added guards, risky calls and type widenings.
Evidence Planner uses a primary pattern from analysis metadata when available, or infers it from these facts.
It assigns fixed priorities: patch anchoring is 100; lifetime and state requirements are 92 for double-free and 89 for use-after-free; null and bounds guards are 90.
Requirements are sorted by decreasing priority, with evidence type breaking ties; the default retains at most eight.
Table~\ref{tab:evidence-routing} shows representative mappings.
These priorities order collection requirements, rather than express confidence in individual facts.
This component uses rules rather than a separately trained or prompted patch-mechanism classifier.

For the CSA comparison, collection is precomputed and the visible view is frozen before editing.
The selected v43 implementation resolves compiler references into at most four function-local CFG witness cards, scoped by the patch and reports.
It compares state associations and helper spelling with the checker, then appends available checker-execution observations.
Additional evidence requests are disabled in this experiment.
The general interface supports bounded, deduplicated role requests; their utility is outside this comparison.

\subsection{Evidence Sources and Roles}
\label{sec:evidence-roles}

\begin{definition}[Analyzer-internal evidence]
An observation is analyzer-internal when its payload comes from an analyzer-produced intermediate representation or from checker callbacks and state observed inside the analyzer, rather than from source text or a final warning alone.
In \toolname, it also identifies the extraction interface and retained raw output, and is bound to the source revision and patch-related file and function.
\end{definition}

Four collectors execute in sequence (Figure~\ref{fig:approach-architecture}b, top to bottom).

\textbf{Patch preflight} identifies changed files, hunks and statements.
This supplies the structural skeleton: \emph{what changed} and \emph{where}.

\textbf{Source extraction} resolves patch files and records bounded contexts around the changed code, including enclosing functions, branch guards, callee signatures, memory and state operations, and build flags.
This provides local semantic context without dumping repository-scale source.

\textbf{Analyzer evidence} records what the backend produces.
In the CSA study, Clang 18's \texttt{debug.DumpCFG} and \texttt{debug.DumpCallGraph} emit UTF-8 dumps.
The collector parses them into \texttt{semweaver.csa\_cfg\_snapshot.v1}, retaining the raw-output SHA-256 and source scope.
They supply CFG branches, value bindings and call edges.

The implementation also observes instrumented CSA callbacks, abstract values and regions, and checker-state associations.
Raw observations use JSONL schema \texttt{semweaver.checker\_trace.v2}; bounded feedback uses \texttt{semweaver.trace\_feedback.v1}.
Original and instrumented scans must preserve diagnostics on both revisions.
These are checker observations, not concrete executions of the vulnerable program.

We distinguish this material from two other origins.
\emph{Analyzer output} comprises diagnostics and alert counts.
\emph{Source-derived} records contain patch diffs, source windows or compile-database-assisted source extraction.
A CodeQL record qualifies as internal evidence only when the database query, revision and returned tuples are retained; the CodeQL example in this study uses source-derived context.

Extraction must handle backend-specific output, instrumentation errors, capped observations and runs with no eligible callback.
We check revision, architecture, source scope and diagnostic parity, and mark unavailable observations explicitly.
Table~\ref{tab:origin-types} accounts for all 193 initial records across 39 subjects.
The 81 internal records comprise 45 guard, 27 state-transition and 9 allocation-lifecycle records.
The 61 source-derived records in this cohort are patch diffs; none is a source-window fallback.
Per-attempt availability is reported in RQ3.

\textbf{Validation feedback} records whether the detector compiles, executes, warns on the vulnerable revision and remains noisy on the fixed revision.
It supplies the failure symptom for the next edit.

The seven persisted types are \texttt{patch\_fact}, \texttt{semantic\_slice}, \texttt{dataflow\_candidate}, \texttt{call\_chain}, \texttt{path\_guard}, \texttt{allocation\_lifecycle} and \texttt{state\_transition}.
They organize changed statements, bounded source context, possible propagation, call context, control conditions, resources and abstract state, respectively.
When a selected role yields no evidence, the bundle retains an explicit missing-evidence marker rather than treating the absence silently, so the refinement agent knows what was requested but unavailable.

\subsection{Evidence Bundle Schema}
\label{sec:evidence-schema}

The normalizer merges all collected facts into the EvidenceBundle shown in Figure~\ref{fig:approach-architecture}c.
Each fact becomes an EvidenceRecord carrying a type, the contributing analyzer, scope, source location, payload, provenance, and an optional EvidenceSlice (the compact semantic content consumed by the agent).
The schema separates program facts from analysis rules in the spirit of relational analyzer frameworks~\cite{avgustinov2016ql,jordan2016souffle,bravenboer2009doop}, but uses a smaller role vocabulary tailored to checker refinement.
Formally:
\begin{equation}
\begin{aligned}
B &= \mathrm{Norm}(E_p \cup E_s \cup E_a \cup E_v),\\
E_a &= E_{\mathrm{CSA}} \cup E_{\mathrm{CodeQL}},\\
r &\in B.records = \langle type, analyzer, scope,\\
&\quad location, payload, provenance, slice\rangle.
\end{aligned}
\label{eq:evidence-bundle}
\end{equation}
Here $E_p$ contains patch facts, $E_s$ bounded source slices, $E_a$ analyzer representations or outputs, and $E_v$ validation outcomes.
The normalizer removes duplicates, records contributing analyzers and retains missing-evidence markers.
Provenance identifies each record as \texttt{analyzer\_\allowbreak internal}, \texttt{analyzer\_\allowbreak output} or \texttt{source\_\allowbreak derived}.
The evidence type and origin are separate: the same role may hold a backend-produced record or a source-derived fallback.
This decouples the bundle from any single backend representation.

\subsection{Paired-Warning Refinement}
\label{sec:refinement}

The refinement agent receives the current detector, the patch, baseline validation notes and a bounded evidence view.
The tool-mediated loop draws on LLM agent and self-refinement architectures, with actions restricted to evidence requests, detector edits and validation commands~\cite{madaan2023selfrefine,shinn2023reflexion,yao2023react,schick2023toolformer}.
The CSA comparison makes zero additional evidence requests.

\subhead{Model and programmatic steps.}
The model proposes checker edits and may supply patch-analysis metadata or enabled role requests.
Preflight rules, normalization, raw-output hashing, source binding, compilation, paired replay and acceptance are programmatic.
The editor prompt gives the current and starting checkers, patch, source and evidence context, symptoms on both revisions, and backend-specific editing and validation rules.
Repair prompts contain the actual compiler diagnostics.
The artifact retains English templates and rendered exchanges, with missing historical exchanges marked.

\subhead{Retention gate.}
A changed candidate must compile and execute normally on both revisions.
Equation~\ref{eq:accept} then retains a recovered vulnerable-side warning, or fewer fixed-side reports while preserving vulnerable-side warning presence.
Fixed-side silence with a vulnerable warning achieves the stronger PDS outcome.
Native refinement additionally checks required hits on controlled array fixtures; Section~\ref{sec:evaluation} describes this guard and the warning-level metrics.

\subhead{Feedback loop.}
When a candidate fails to compile or improve the retained result, its code and feedback remain available for the next attempt.
The agent edits the latest attempt, while $D^*$ stores the best retained checker.
Algorithm~\ref{alg:evidence-guided-refinement} gives the loop; the protocol specifies its stopping conditions and treatment of interrupted executions.
CSA checkers are compiled and replayed against both revisions, while CodeQL queries run over the corresponding databases.

\subhead{Adding a backend.}
An adapter provides registration, evidence and provenance mapping, dependencies, execution and result decoding, and paired validation.
Shared modules still contain backend branches.
The four CodeQL-specific modules occupy 2,438 physical lines, including comments and generation code.
With an analyzer and patch pair already available, we estimate that a familiar developer using Codex could complete a basic adapter within an afternoon; developer time was not measured.
New native-evidence semantics and broad validation require additional work.
A new bug mechanism needs a role mapping and fixtures for safe and unsafe cases, with a new extractor where a required relation is unavailable.
