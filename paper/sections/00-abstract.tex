LLM-based patch-driven synthesis can automatically generate static vulnerability checkers from security fixes, but the resulting checkers often capture only the syntactic shape of the patch while missing the semantic conditions needed to distinguish vulnerable code from fixed code.
Compiler errors and warning reports help refine these checkers, yet do not always explain which condition needs to change.
We observe that static-analysis engines also expose how the program is represented and how a checker uses that representation.
\toolname is a plug-in refinement layer that collects patch-relevant analyzer evidence and combines it with source context and validation feedback in a typed evidence bundle.
The agent edits the existing checker, while paired validation retains recovered vulnerable-side warnings or fewer fixed-side reports.
We evaluate \toolname on 39 generated-only KNighter CSA checkers.
Native-evidence refinement reaches 23 warning-positive vulnerable revisions, compared with 15 for KNighter's refinement loop, and raises version-level $F_1$ from $0.448$ to $0.575$.
Without internal evidence, $F_1$ is nearly identical and the total fixed-side burden is lower.
Within the complete 15-case initially noisy group, native refinement reduces fixed reports from 69 to 44, mainly through one case.
Repeated decodes, a three-model subset and an automatic CodeQL example examine the workflow under other settings.
A follow-up of all 11 non-tied comparisons shows how evidence helps repair checker recognition, and why the resulting warning can still concern the wrong object, scope or path.
